# 晶途拾光 · Crystal Trail

一部按《晶途拾光_8bit像素游戏设计与开发规格书》实现的 8-bit 像素平台解谜游戏。
无战斗、无敌人、无生命值、无死亡惩罚；安静地探索、把机关想明白、把宝物收齐。

## 网页入口

**方式一（推荐，存档最稳）** —— 起一个本地静态服务，浏览器打开：

```powershell
node tools/serve.mjs            # 默认 http://127.0.0.1:8777/
node tools/serve.mjs --port 8788
```

**方式二（零依赖）** —— 直接双击 `index.html`，用 `file://` 打开。
Edge / Chrome 实测可用，包括 localStorage 存档；个别浏览器会禁用 `file://`
下的 localStorage，此时游戏仍可玩但进度不落盘，所以优先用方式一。

两种方式都不需要联网、不需要安装任何东西。

## 怎么玩

| 操作 | PC | 安卓 / 触屏 |
|---|---|---|
| 移动 | `←` `→` 或 `A` `D` | 左下角虚拟摇杆（八向吸附） |
| 跳跃 | `空格` / `J` | 右下角跳跃键（支持长按控制高度） |
| 交互 | `E` / `回车` / `F` | 交互键（与跳跃键分离） |
| 穿透平台 | 按住 `↓` | 摇杆下拉 |
| 暂停 | `Esc` / `P` | 右上角暂停键 |

也支持 Xbox 布局手柄（左摇杆移动、A 跳跃、X 交互、Start 暂停）。

游戏内共 25 关、5 个主题、60 件拾遗宝物、5 枚本源彩晶、5 枚守护印记。
进度自动存 `localStorage`，3 个手动槽位 + 1 个自动槽位。

**新功能（后续需求）**

- **取名**：新建存档时可自己输入主角名字（走隐藏 `<input>`，中文输入法可用），
  或点「随机」骰子按钮从名字池抽取。默认预填一个随机名，直接回车即可开局。
- **静音开关**：设置页各有「关闭音乐」「关闭音效」独立开关，状态写进存档。
- **中英双语**：设置页可切换，存档记忆。英文版包含 395 条翻译文本与 74 条界面文案。
- **教程**：第一关首次游玩时出现按键提示（移动 → 跳跃 → 长按跳更高），
  真正做出动作才推进，不锁操作。
- **旅途留影**：每拾起一枚本源彩晶，图鉴解锁一张 192×128 的场景插画
  （程序化合成的独立构图，不是游戏截图）＋标题＋文案；
  五张连起来是一条完整故事线，集齐五枚彩晶后在图鉴末页显示全文。

**生命值**：一局 3 条命（HUD 左上角三颗心）。掉进沟里、或被来回滚动的**滚石**撞到，
各扣 1 条并立刻在最近的石碑复活，画面不会卡住；复活后有 1 秒无敌（主角会闪烁）。
三条命用完时本关从头再来，已收集的宝物保留。

## 这一版的关键数字

| 指标 | 规格书要求 | 实测 |
|---|---|---|
| 内部渲染分辨率 | 480 × 270，整数倍放大 | 480 × 270，2~4 倍整数缩放 |
| 单帧耗时 | 60 帧（16.67 ms 预算） | p99 **1.17 ms**，p50 0.75 ms（14 倍余量） |
| 热路径分配 | — | 600 帧堆内存增量 **−0.15 MB** |
| 关卡规模 | 120~180 × 24~40 格 | 166~259 × 28~32 格（长度按后续需求 +40%） |
| 关卡长度递进 | — | 章内逐关变长、章间逐章变长（各章第 1 关：166→175→192→198→206 格） |
| 关卡布局 | — | 每关随机抽一种结构：起伏 / 多坑 / 阶梯 / 塔台 |
| 垂直落差 | 至少 1 处 ≥ 6 格 | 统一封顶 6 格，不再出现整屏高墙 |
| 每屏装饰 | ≥ 8 个 | 最少 7 个（后续需求下调，见「与规格书的偏差」） |
| 装饰总数/关 | ≥ 40 个 | 60~109 个 |
| 主题调色板 | 16 色 | 16 色 × 5 主题 + 全局 32 色 |
| 单张素材色数 | ≤ 24 色 | 瓦片集最多 12 色，精灵最多 17 色 |
| 主角单帧色数 | ≤ 12 色 | 12 色 |
| 中文字库 | 12 × 12 点阵 | 7472 字形（GB2312 全集），0 缺字 |
| 对话打字速度 | 24 字/秒 | 24 字/秒（实测 1.0 秒 24 字） |
| 美术校验 | Pillow 四项检查 | 36 个素材，0 项不合格 |

## 自检

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File verify.ps1
```

12 步全绿才会打印「全部通过」。各步含义：

| 步骤 | 检查内容 |
|---|---|
| 1 | 生成 25 关并逐关核对 §5.3 规模指标与 §5.4 装饰密度、跳跃可达性 |
| 2 | 文本语料 §6.4 长度/禁用词/语气/字库覆盖 |
| 3–4 | 打包 `data.js`、生成 `index.html` |
| 5–6 | 导出美术 PNG 并跑 Pillow 校验（§7.7 四项） |
| 7 | 行为自检：出口触发、快速复位、存档往返、打字机速率 |
| 8 | 用真实 `main.js` + DOM 桩启动浏览器入口，确认能出画面 |
| 9 | 25 关各跑 180 帧物理 + 渲染，抓任何异常 |
| 10 | 逐关实测帧耗时与堆增量 |
| 11 | 机器人走位，确认地形本身不会卡死玩家 |
| 12 | 真实 Edge/Chrome 引擎（CDP）：启动、按键、帧率、存档、触屏控件 |

单独跑某一项也可以，例如：

```powershell
node tools/qa_perf.mjs          # 性能
node tools/qa_game.mjs star-05  # 单关截图到 build/qa/
```

## 架构上几个刻意的选择

**纯软件渲染器。** 480 × 270 的 `Uint32Array` 帧缓冲，所有绘制都自己写像素，
浏览器与无头 QA 走的是同一条代码路径。因此 `build/qa/` 里的截图就是玩家看到的
画面，不存在「截图和实机不一样」。

**固定步长 1/60 + 渲染解耦。** 逻辑按固定步长推进，渲染每个 `requestAnimationFrame`
一次。在 30 Hz / 60 Hz / 144 Hz 屏幕上手感完全一致，也会在标签页切回来时
把累积时间钳在 0.25 秒，避免一次性补几百步。

**美术全部程序化生成。** 瓦片按「8 邻接掩码 × 4 变体 × 3 种埋深」按需生成并缓存，
所以地面是「草皮 → 土层 → 深层岩体」三层过渡，而不是一整块扁平色块；
换主题只换调色板与配方，不换流程。

**音频现场合成。** 四声道 chiptune（2 方波 + 1 三角波 + 1 噪声）用 WebAudio 现算，
包里没有一个 OGG 文件，因此离线可玩、包体极小。

## 与规格书的偏差

完整对照见 `晶途拾光_实现说明与规格符合性报告.docx`。要点：

0. **后续需求对原始数值的覆盖**：长度 +40%（§5.3 的 120~180 → 166~259）、垂直落差封顶 6 格、每屏装饰 8 → 7（§5.4）、装饰微动只在站立时生效、新增生命值与滚石障碍（推翻 §1.4/§12 的「无生命值」）。全部按你的要求实现，并在符合性报告第五章逐条记录。
0b. **生命值机制**：你后续要求「一局三条命 + 撞障碍扣命」，这**推翻**了规格书
   §1.4 与 §12 里「全程无生命值、无死亡惩罚」的不可协商基线。已按新需求实现，
   并在符合性报告里保留原条款、标注为已覆盖，而不是悄悄改成满足。
1. **引擎**：规格书 §9.1 指定 Godot 4。本机没有 Godot / JDK / Android SDK，
   无法产出 `setup.exe` 与签名 APK，因此改用 HTML5 + 自研软件渲染器交付，
   并把 §7 全部像素规格（480×270、整数缩放、16px 瓦片、调色板、动画帧率）
   逐条实现。代价是 §10 的双端打包链路未交付。
2. **§4.3 台阶高度**：规格书未规定爬升上限。本作把地面台阶限制在 2 格（32 px），
   因为 3 格（48 px）相对 52.8 px 的最大跳高只剩 9% 余量，与「治愈、安静」的
   定位不合。难度改由机关数量与谜题链长度承担（与 §5.5 末句一致）。
3. **§5.3 屏宽换算**：原文「120~180 格 ≈ 1.9~2.9 屏宽（单屏 64 格）」与
   §7.1 的 480 px / 16 px = 30 格/屏 冲突。本作按 120~180 格实现，
   实际为 4~5.8 屏宽。
4. **§6.4 对话框**：160 × 64 面板配 12 px 汉字，可用宽 148 px，故折行为
   每行 12 字（满足「每行不超过 18 个汉字」），单句 12~18 字正好占两行。
5. **§4.3 表 5-1 与表 4-2 冲突**：表 5-1 写「第 1 关支线宝物 1 件」，
   与表 4-2「每关 2~3 件、全局 60 件」及表 5-3 冲突。本作按 60 件总量实现，
   每单元 2/2/2/3/3。
6. **§9.5/§9.6 Harness 接入**：按规格书给出的「无后端」分支执行 ——
   全部文本在构建期预生成并打进包内，运行时纯离线（§9.6 原文允许此方案）。
